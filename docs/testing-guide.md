# 測試完整度指南

> **定位**：跨專案的參考文件,不綁 ChatSystem。ChatSystem 的程式碼只當例子出現,因為抽象的建議沒有人記得住。
>
> **要回答的問題**：「我怎麼知道測試夠不夠?不夠的話該補什麼?」
>
> 不在範圍內：怎麼寫第一個單元測試、xUnit/NUnit 的語法、mock 框架用法。這份文件假設你已經在寫測試了,想知道**下一步**。

---

## 0. 先問清楚「更全面」是哪一種

這是最常被跳過的一步。「測試不夠全面」是四種不同的問題,工具完全不同:

| 想涵蓋更多的… | 該拿的工具 | 章節 |
|---|---|---|
| **輸入值** | property-based testing | §2 |
| **操作序列** | model-based testing | §3 |
| **併發交錯 / 失敗模式** | 確定性模擬 + fault injection | §4 |
| **組裝與設定** | 不變量測試 / 架構測試 / analyzer | §5 |
| **「我怎麼知道現在夠不夠」** | 變異測試 | §1 |

拿錯工具的症狀很典型:加了一堆 property test,結果 bug 還是出在 DI 註冊漏了一行。**先分類再選工具。**

---

## 1. 先量測:變異測試（mutation testing）

**行覆蓋率會騙人。** 它只說「這行被執行過」,不說「這行壞掉時會不會有測試紅」。一組把所有斷言都刪掉的測試,覆蓋率一樣漂亮。

變異測試直接回答那個問題:工具自動把你的程式碼改壞（`>` 改成 `>=`、`&&` 改成 `||`、回傳值改成 `null`、把一整行刪掉),每改一次就跑一次測試。

- 測試紅了 → 這個變異被**殺死**,你的測試在這裡是有效的
- 測試還是綠的 → 變異**存活**,代表這段邏輯壞掉不會有人發現

**存活的變異就是你的測試缺口清單**,而且是具體到行的。

.NET 上是 **Stryker.NET**（`dotnet stryker`）。

實務建議:

- **不要對整個 solution 跑**,很慢（每個變異都要跑一次測試）。挑核心邏輯的專案或資料夾。
- 目標不是 100%。有些變異在語義上等價（`i++` vs `++i` 在某些位置),殺不掉也不該殺。
- **最好的用法是當診斷,不是當 gate。** 跑一次、看存活清單、挑真的重要的補測試,而不是把 mutation score 綁進 CI 門檻。

**什麼時候該跑**:當你覺得「測試好像不少但心裡不踏實」的時候。它會告訴你不踏實是對的還是錯的。

## 2. Property-based testing（基於性質的測試）

不寫「這三個輸入 → 這三個輸出」,而是寫**對所有輸入都該成立的性質**,由框架產生上百上千組輸入,失敗時自動 **shrink** 成最小反例。

Shrink 是關鍵價值:框架找到一個 200 字元的失敗字串,會自動縮到「其實只要是空字串就會爆」。

### .NET 工具

| 工具 | 特點 |
|---|---|
| **CsCheck** | C# 原生,shrink 做得好,而且**內建 model-based 與併發測試**（§3、§4 都用得到）。C# 專案首選 |
| **FsCheck** | 最成熟、生態最大,3.x 之後 C# API 改善不少,但骨子裡還是 F#-first |
| **Hedgehog.NET** | 產生器與 shrink 綁在一起（不需要另外寫 shrinker),概念上更乾淨 |

### 真正的瓶頸:想不出性質

工具十分鐘就會用,難的是「我要斷言什麼?」。大部分人卡在這裡,最後寫出一堆換湯不換藥的範例測試。

**下面這張表是解法。** 遇到一段程式碼,照著問一遍,通常會中兩三個:

| 性質形狀 | 長相 | 典型對象 |
|---|---|---|
| **來回 (round-trip)** | `decode(encode(x)) == x` | 序列化、編碼、壓縮、parse |
| **模型比對 (oracle)** | `real(x) == 明顯正確但很慢的實作(x)` | 有簡單參考實作的任何東西 |
| **不變量 (invariant)** | 操作前後某個性質恆成立 | 排序後長度不變、集合元素相同 |
| **冪等 (idempotence)** | `f(f(x)) == f(x)` | 清理、正規化、任何「重複執行要安全」的東西 |
| **交換 / 結合** | 順序或分組不影響結果 | 合併、聚合 |
| **分而治之** | `f(整體) == 合併(f(部分))` | **分頁**、批次處理、map-reduce |
| **蛻變關係 (metamorphic)** | 不知道正確答案,但知道兩次執行之間的關係 | 「多一筆輸入,輸出只多那一筆」 |
| **不該當機 (fuzz)** | 任何輸入都不該丟未預期的例外 | parser、外部輸入的入口 |

> **蛻變關係特別值得記住**,因為它解決了「我根本不知道正確答案是什麼」的情況——那正是最難寫測試的情況。你不必知道搜尋結果應該是什麼,但你知道「多加一筆符合的資料,結果應該多一筆」。

### 例子（ChatSystem）

- **`MonotonicMicrosecondSequencer`**（不變量 + 併發）——「N 個執行緒併發呼叫 `Next()`,結果兩兩相異且嚴格遞增」。非原子的實作在單執行緒測試下**永遠會過**,只有併發 property 撞得出來。
- **keyset 分頁**（分而治之)——「用任意 page size k 一路翻完,拼起來恰好等於一次讀完的結果,不重不漏」。邊界情況（游標正好落在某則訊息、空頁、最後一頁、稀疏鍵)手寫測試不會想到,產生器會。
- **protobuf 型別**（來回)——對 registry 裡每個註冊型別斷言 `ParseFrom(ToByteArray(m))` 等於 `m`。
- **`RoomPassword`**（不變量)——`Verify(p, Hash(p))` 恆真;`q ≠ p` 時恆假。
- **`RemoveAsync` / sweeper / 保留期清理**（冪等)——多複本環境下重複執行必須安全。

## 3. Model-based testing（模型比對測試）

property testing 的有狀態版本,也是**最接近「自動產生測試案例」**的東西。

做法:

1. 寫一個**明顯正確但很笨**的模型（通常就是 `Dictionary` + 一個假時鐘）
2. 框架產生**隨機的操作序列**
3. 同時打在真實實作與模型上,斷言兩者**永遠一致**

價值在於它會產生你不會手寫的序列——`Join → 斷線 → 時鐘前進 25 秒 → Join → 時鐘前進 10 秒 → 讀取` 這種。

CsCheck 與 FsCheck 都有這個能力（CsCheck 的 model-based sample、FsCheck 的 `Command`/`Machine`）。

**最適合的對象:store 與狀態機。** 判準是「這個元件有多種操作,而且**操作順序會影響結果**」。順序不影響結果的東西不需要它。

例子:`IRoomMembership` 有 join / remove / 斷線標記 / 寬限期到期 / 讀取時過濾五種互動,而 fencing 的正確性完全取決於順序。模型就是一個 dict 加一個可推進的時鐘。

**注意:替身要夠笨。** 如果模型跟實作一樣複雜（甚至共用邏輯),你只是在測自己寫的替身。模型的價值來自它笨到一眼看得出對。

## 4. 確定性模擬與 fault injection

分散式系統的 bug 幾乎都在**時序**上:訊息遲到、亂序、重送、節點在最壞的那一刻掛掉。這些用一般測試碰不到,因為它們需要特定的交錯。

做法（FoundationDB 開創,TigerBeetle、Antithesis 沿用）:

1. 整個系統跑在**單一 process**、單一執行緒
2. 排程、逾時、隨機性全部來自**固定種子的 PRNG**
3. 注入故障:訊息遺失、亂序、延遲、重複、節點崩潰、時鐘偏移
4. 跑幾千次,每次不同種子
5. 失敗時**只要記下種子就能完整重播**

第 5 點是整套方法的重點。併發 bug 最痛的不是難發現,是**發現了無法重現**。

### 你的專案可能已經蓋好一半

判斷有沒有這個基礎,看三件事:

- [ ] 有沒有一個**能把跨 process 通訊收進 process 內**的模式?（in-memory bus、fake transport、`Adaptare.Direct` 這類）
- [ ] 時間有沒有**可注入**?（.NET 就是 `TimeProvider`,不要直接用 `DateTime.Now`)
- [ ] 隨機性有沒有集中?（不要散落的 `Guid.NewGuid()` / `Random`)

三個都有的話,離確定性模擬只差「可控排程 + 故障注入鉤子 + 種子」。

> ChatSystem 的 `Integration.Tests` 正好三項都符合（`Adaptare.Direct`、in-process、0.6 秒、`TimeProvider` 可推進),這種底座比想像中值錢。

**互補的作法:從外面打（Jepsen 式）。** 不控制內部排程,而是把真實叢集跑起來,從外部併發下指令、同時用網路分區工具製造故障,事後檢查歷史紀錄是否符合線性一致等性質。更貼近真實,但不可重播。兩種方法抓到的東西不一樣。

## 5. 組裝層的 bug:不變量測試、架構測試、analyzer

**這一節是最容易被忽略的,因為上面那些技術一個都蓋不到。**

§2–§4 全部作用在「演算法與狀態機」層。但很多真實 bug 出在:

- DI 註冊漏了、註冊兩次、生命週期錯（singleton 抓了 scoped)
- 設定檔的鍵名打錯、環境變數沒帶到
- 序列化的邊界行為（預設值、null、空集合)
- 用錯了某個「長得很像但語意不同」的東西（例如拿 request-scoped 的 `CancellationToken` 去做清理）

對症的三種工具:

### (a) 掃過註冊表的不變量測試

如果系統有「一張所有型別/handler/subject 的表」,就對**整張表**斷言性質,而不是逐一寫測試。新增項目自動被涵蓋。

> **真實案例**:ChatSystem 的 `InboundAck.OK` 原本是 `0`,而 proto3 不序列化預設值 → 成功的 ack 是 **0 bytes** → 經過 NATS 回來變 `null` → **每一個成功的命令都殺掉連線**。單元測試抓不到（mock 回傳 `byte[0]`,而 `ParseFrom(byte[0])` 是合法的),只有真的 NATS 往返會把 0 bytes 變成 `null`。
>
> 歸納出的教訓是「任何全欄位都是預設值的 protobuf 訊息序列化後是 0 bytes」,而**那條教訓可以直接寫成掃過整個 registry 的測試**:每個下行 reply 型別在成功路徑上都必須序列化成非空 bytes。寫一次,以後每個新增的型別自動被檢查。

**通用原則:每次你歸納出一條「以後要注意」的教訓,先問它能不能變成一條掃過全表的斷言。** 能的話就不必靠記憶力。

### (b) 架構測試

用 NetArchTest.Rules 或 ArchUnitNET 把「層次不能反向依賴」「這個命名空間不能引用那個」寫成測試。

適合釘住那些**寫在文件裡但沒有任何機制保證**的規則。文件會過期,測試不會。

### (c) 自訂 Roslyn analyzer

當一條規則是「某種寫法在某種脈絡下永遠是錯的」,analyzer 比測試更適合——它在編譯期就擋掉,而且對**還沒寫出來的程式碼**也有效。

> **真實案例**:斷線清理用了 minimal API 注入的 `CancellationToken`,而那就是 `HttpContext.RequestAborted`——**client 一斷線它就已經被取消**,等於「因為連線斷了,所以不清理連線」。這種錯在 diff 上完全看不出來,而且會不斷有人重犯。一條 analyzer 規則（清理路徑不得使用 request-scoped token)比十條測試有效。

## 6. 測試分層之間的縫隙

多數專案有兩到三層測試。**bug 特別喜歡住在層與層之間的縫隙裡**,因為每一層都假設「那個是另一層的責任」。

典型的三層與各自蓋不到的東西:

| 層 | 蓋得到 | **結構性蓋不到** |
|---|---|---|
| 單元（全 mock) | 分支邏輯、演算法 | 元件之間的接線;mock 的行為與真實不符之處 |
| 整合（真元件、假傳輸) | 元件組合、流程 | wire format;真實傳輸的邊界行為;跨節點 |
| 端到端（真環境) | 全部 | 太慢,所以跑不勤 → 等於部分沒在跑 |

**「結構性蓋不到」那一欄要明確寫下來**,寫在測試專案的 README 或設計文件裡。沒寫下來的話,每次出事都要重新推導一次「為什麼這個沒被抓到」。

> ChatSystem 的三個真實 bug **全部落在縫隙裡**:`InboundAck` 的 0 bytes（只有真 NATS 會把 0 bytes 變 null)、DI 重複註冊（只有真實組裝看得到)、cancellation token（只有真 Kestrel 會觸發 `RequestAborted`)。這不是巧合——**能被單層蓋到的 bug 早就被蓋掉了,留下來的都在縫隙裡。**

實務作法:

- 每修好一個 bug,問**「為什麼現有的層都沒抓到?」**,答案就是縫隙的位置。
- 端到端測試**預設 skip、用環境變數開啟**是個好折衷（跑不動的測試等於沒有測試),但要有人定期跑,而且 CI 至少每天一次。
- 端到端測試要**斷言它宣稱要驗的東西**。例如驗「跨節點」就要真的斷言兩條連線落在不同節點上,否則哪天都落在同一個節點,測試還是綠的,但它已經不驗任何東西了。

## 7. 形式化驗證放在哪裡

**它不會產生測試。** 模型檢查（TLA+、Alloy）驗的是你寫的**模型**,產出是「性質成立」或一條反例軌跡,不是測試程式碼。而且模型與實作之間的落差不在保證範圍內。

它對測試的真正貢獻是間接但實在的:

> **property-based testing 的瓶頸是「我要斷言什麼性質」,而形式化的思考方式強迫你把不變量寫出來。**

所以順序應該是:

1. 先把設計文件裡已經用自然語言寫出來的不變量,翻成 property / model-based 測試
2. 真的遇到「講不清楚這個不變量到底成不成立」的時候,再拿 TLA+ 去釘**那一個點**

不要為了用而用。TLA+ 有明確的問題要回答時才有價值。

**判斷「這個問題值得用 TLA+ 嗎」的三個訊號**:

- 涉及**多個並行參與者**與共享狀態
- 你已經寫了一段散文式的正確性論證,但自己不太確定它對不對
- 出錯的代價高,而且**錯了不會有聲音**（資料靜默損壞、順序靜默錯亂,而不是當機）

三個都中的話值得。只中一個通常不值得。

## 8. 對照表:症狀 → 工具

| 症狀 | 先試 |
|---|---|
| 「測試不少但心裡不踏實」 | 變異測試（§1),先量測再補 |
| 「總是有沒想到的輸入」 | property-based testing（§2) |
| 「特定操作順序才會壞」 | model-based testing（§3) |
| 「偶爾失敗,重跑就過」 | 確定性模擬（§4);在那之前先確認時間與隨機性可注入 |
| 「本機好好的,上線就壞」 | 組裝層（§5)——DI、設定、序列化邊界 |
| 「這個 bug 為什麼沒被抓到」 | 縫隙分析（§6),然後補在對的那一層 |
| 「我不確定這個設計對不對」 | 這不是測試問題,是設計問題（§7) |

## 9. 反模式

- **追求覆蓋率數字。** 行覆蓋率 90% 而斷言薄弱,不如 60% 而斷言紮實。要量測完整度就用變異測試。
- **模型跟實作一樣複雜。** model-based testing 的模型必須笨到一眼看得出對,否則你在測自己寫的替身。
- **在替身上驗證只有真實元件才有的性質。** 例如用 in-memory 的 store 去驗「交易的原子性」——那個替身怎麼寫都會通過。**先問「這個性質是誰提供的」,再決定測試放哪一層。**
- **端到端測試慢到沒人跑。** 跑不動的測試等於沒有測試,而且更糟——它給人已經測過的錯覺。
- **為了測試而破壞設計。** 把私有的東西改成 public 只為了測它,通常代表測試的切入點選錯了。
- **測試沒有斷言它宣稱要驗的東西。** 最隱蔽的一種:測試名字叫 `CrossNode_Broadcast`,但沒有任何一行確認那兩條連線真的在不同節點。

## 10. 落地順序

如果現在什麼都還沒有,建議這個順序（每一步都能單獨產生價值,不必一次做完):

1. **確認時間與隨機性可注入**（`TimeProvider`、集中的 seed）。這是後面所有東西的前提,而且事後補很痛。
2. **跑一次變異測試**,拿到具體的缺口清單。
3. **把設計文件裡的不變量翻成 property test。** 從「來回」與「分而治之」這兩種形狀開始,它們最容易找也最容易寫。
4. **對最複雜的那個有狀態元件做 model-based testing。**
5. **把歸納出來的教訓寫成掃過全表的不變量測試**(§5a),讓它們不依賴記憶力。
6. **記錄每一層「結構性蓋不到什麼」**(§6),並在每次修 bug 後回頭更新。
7. 有跨 process 的時序問題再考慮**確定性模擬**。
8. 有講不清楚的併發不變量再考慮**形式化驗證**。

前三步通常就能解決大部分「測試不夠全面」的感覺。
